# Тестовое задание: Асинхронный сервис процессинга платежей

## Описание

Необходимо реализовать микросервис для асинхронной обработки платежей. Сервис принимает запросы на оплату, обрабатывает их через внешний платёжный шлюз (эмуляцию) и уведомляет клиента о результате через Webhook.

## Сущности

### Платёж (Payment)

- ID платежа — уникальный идентификатор
- Сумма — `Decimal`
- Валюта — `RUB`, `USD`, `EUR`
- Описание — строка
- Метаданные — JSON-поле для дополнительной информации
- Статус — `pending`, `succeeded`, `failed`
- Idempotency Key — уникальный ключ для защиты от дубликатов
- Webhook URL — адрес для уведомления о результате
- Даты создания и обработки

## Функционал API

### 1. Создание платежа

`POST /api/v1/payments`

**Заголовок:** Idempotency-Key обязательный API-ключ.

**Body:** сумма, валюта, описание, метаданные, `webhook_url`.

**Ответ:** `202 Accepted`, `payment_id`, статус, `created_at`.

### 2. Получение информации о платеже

`GET /api/v1/payments/{payment_id}`

**Ответ:** детальная информация о платеже.

## Технические требования

### Брокер сообщений

При создании платежа публикуется событие в очередь payments.new.

Один consumer выполняет следующие действия:

- Получает сообщение из очереди
- Эмулирует обработку платежа (2–5 секунд, 90% успеха, 10% ошибки)
- Обновляет статус в БД
- Отправляет Webhook-уведомление на указанный URL
- Реализует повторные попытки при ошибках отправки

### Гарантии доставки

- **Outbox pattern** для гарантированной публикации событий
- **Idempotency Key** для защиты от дубликатов
- **Dead Letter Queue (DLQ)** для сообщений, не обработанных после 3 попыток

### Аутентификация

Статический API-ключ в заголовке `X-API-Key` для всех эндпоинтов.

## Стек технологий

- FastAPI
- Pydantic v2
- SQLAlchemy 2.0 (асинхронный режим)
- PostgreSQL
- RabbitMQ (FastStream)
- Alembic (миграции)
- Docker
- Docker Compose

## Требования к результату

1. **Модели и миграции:** таблицы `payments` и `outbox`
2. **API-эндпоинты:** создание и получение платежа
3. **Consumer:** один обработчик, выполняющий все необходимые действия
4. **Outbox pattern:** гарантированная доставка событий
5. **Retry:** 3 попытки с экспоненциальной задержкой
6. **Dead Letter Queue:** для окончательно упавших сообщений
7. **Docker:** Compose-файл с сервисами PostgreSQL, RabbitMQ, API и consumer
8. **Документация:** README с инструкциями по запуску и примерами запросов

## Критерии оценки

- Архитектура и чистота кода
- Корректная реализация Outbox pattern
- Работа с RabbitMQ: очереди, обменники, DLQ
- Идемпотентность
- Обработка ошибок и логика повторных попыток
- Работоспособность Docker-окружения
